# NoteLah local hybrid RAG

Implemented as a desktop-only Chat view. The chat model is Qwen 3.5 2B through local Ollama; nomic-embed-text creates embeddings. Both are independently selectable from locally installed, capability-checked models. No model downloads occur inside the app. The development setup installed nomic-embed-text alongside the existing Qwen model.

## Storage and ingestion

The existing `notelah.sqlite` and managed `files/` remain the source of truth. The derived `search-index.sqlite` stores one JSON chunk/vector record per document, plus an embedding identity. This is an embedded exact-search vector store, not a separate vector database server or an approximate nearest-neighbor index. Backups retain source notes and files; the search cache is rebuilt when needed. Chat messages remain in renderer memory for the current session. Model selections are saved in localStorage.

When a question arrives, the backend snapshots saved notes, fingerprints title/body/folder/file metadata, and reuses unchanged documents. New or edited documents are extracted, chunked, embedded in batches of eight, and persisted atomically. Deleted notes are absent from the replacement index. Model name, model digest, and chunker version invalidate incompatible embeddings. A library change during indexing or answering rejects the stale result. Cancelled or failed indexing leaves the previous cache intact.

TXT/Markdown text comes from the imported body stored in SQLite; written notes use the same body. PDFs are read from their verified managed copies and processed by Mozilla PDF.js. Each page is independently chunked, preserving one-based PDF page references. No OCR is included: scanned PDFs without text and unreadable/encrypted PDFs surface indexing notices. There is a 500-page/2-million-character PDF limit and 5,000-chunk library limit.

Chunks target 1,000 characters with 120-character overlap within a section, preserving page boundaries. Markdown headings, common plain-text section headings, and conservative PDF font-size hints identify sections. Each chunk retains its section heading, document-wide chunk index, and start/end offsets into its normalized page text. Titles and headings are included in embeddings and BM25. The cache identity is `sections-v2`, so the old derived index rebuilds without changing source data. PDF geometry preserves line breaks and separates distant same-baseline text; stream order is preserved rather than guessing a universal multi-column layout. Complex layouts and OCR remain limitations.

## Retrieval and generation

1. Apply the selected folder scope before retrieval. All-library indexing currently happens on each question, with unchanged embeddings reused.
2. Unicode-normalized lowercase word tokens feed a TypeScript BM25 implementation (k1=1.2, b=0.75). SQLite's existing sql.js build lacks FTS5; no FTS5 support is assumed. BM25 is calculated over the scoped collection. A small, visible English alias map expands common field vocabulary (for example study → education/degree/qualifications and specialty → skills/projects). It adds no user facts or prior conversation and is shown separately as the keyword query. Vector search still embeds the standalone question.
3. Embed the independent or explicitly resolved question with nomic's `search_query:` prefix; document embeddings use `search_document:`. Compute exact cosine similarity over cached vectors. The implementation currently applies these prefixes to all selectable embedding models; other models may not benefit from nomic's conventions.
4. Take up to 20 positive-score results from each search, then reciprocal rank fusion with k=60 and equal weights: score(chunk) = sum(1 / (60 + rank)). Missing ranks contribute zero. RRF scores are not probabilities or confidence values.
5. Select context separately from candidate ranking. Merge overlapping chunks within the same page/section, remove exact duplicate passages, and fill remaining space with same-section neighbours. A short document can be included in full when it is the sole document in scope or both search methods place its leading chunk in their top three. There is no three-chunk document cap. Up to 16 merged sources fit an exact JSON source-byte budget. Positive cosine similarity and retrieval agreement are not calibrated confidence measures.
6. Send the latest question, resolved standalone question, numbered sources, and grounding instructions using separate system/user messages. Earlier answers are excluded from generation. Generation uses an 8,192-token context setting, an 800-token output cap, temperature 0.1, thinking disabled, and a JSON schema for `kind` (answer, inference, insufficient) and a list of claims. Every claim must supply text and an array of source numbers constrained to the labels actually available. Simple fact questions are limited to one claim; specialty/multipart questions to two, while explicit summaries/lists can use up to five. The application constructs clickable citations from those arrays instead of relying on the model to remember bracket formatting. Context is selected against the exact remaining space in the final 6,500-UTF-8-byte prompt budget; oversized questions are rejected. This conservative byte bound is not a model-specific tokenizer measurement.
7. Parse and validate structured claim text and source arrays. Label inferences explicitly. Withhold malformed output and answers with missing or invalid numeric citations; an insufficient-evidence response uses a fixed abstention rather than displaying potentially unsupported model text. Source links and retrieved evidence remain inspectable. Valid labels still do not prove entailment; no automated semantic citation verifier is claimed. Output truncation is reported.

Standalone questions use their own text only. Explicit referential/elliptical follow-ups trigger a separate bounded Qwen resolution request with a structured JSON response. It substitutes conversation references without answering or appending previous topics. Ambiguous, failed, or still-unresolved rewrites request clarification rather than silently polluting retrieval. The heuristic gate is intentionally simple and is not a perfect linguistic classifier. Only the latest prior turn is used for resolution; its old citation labels are stripped. Generation receives no prior answer history. Changing the folder starts a new conversation. Search details show the original/resolved query, rewrite flag, candidate counts, context bytes, and elapsed time.

## Local runtime and boundaries

Only fixed localhost Ollama endpoints are used, with HTTP redirects refused. Model discovery checks capabilities and excludes declared remote/cloud models. Renderer IPC is restricted to the trusted app frame, with request validation. Long inference is independent of the workspace save queue; only one RAG job runs at a time and Stop aborts network requests and PDF work. Models use `keep_alive: 0` to release memory after each embedding batch or answer; this favors memory over loading speed. A cancelled request is aborted, but actual model unloading timing is controlled by Ollama.

Document text is untrusted prompt data. The system prompt instructs the model not to follow document commands, but this does not guarantee prompt-injection resistance. The model has no tools and cannot change notes, tasks, or files. Answers and source text are rendered as escaped React text. Clicking a source shows its retrieved passage and current text, or opens its managed PDF; the built-in viewer does not yet jump to the cited page.

## Validation and interview discussion

`npm test` now runs 22 tests, including a byte-for-byte check that rebuilding an older search index cannot change the source database. It covers BM25 and fusion behavior, chunk bounds, persisted embedding reuse, folder scoping, edit/deletion invalidation, model-digest invalidation, cancellation, stale indexing rejection, PDF page extraction, invalid-PDF notices, and withholding uncited answers, alongside existing storage tests.

After `npm run build`, `node scripts/chat-qa.cjs` uses isolated data under `work/` and real installed Ollama models to verify the desktop question-to-answer path, PDF citations, source preview, folder scope, session retention across navigation, narrow layout, and cancellation. `node scripts/notes-qa.cjs` checks Notes regressions.

Run `npx tsx scripts/evaluate-rag.ts` for a fixed synthetic fixture corpus and ten section-labelled questions. It uses actual local nomic embeddings, compares keyword/vector/hybrid Recall@3 and MRR, measures selected-context evidence coverage, and writes a JSON report under ignored `work/`. It does not read the user database. This small fixture evaluation is not proof of production superiority: the observed run had Recall@3 of 0.90 / 1.00 / 1.00 for keyword/vector/hybrid, while vector MRR (0.95) exceeded hybrid MRR (0.80). RRF remains an evaluated baseline rather than an assumed universal improvement. Ranking timing excludes embedding/generation; total embedding time is reported separately.

Run `node scripts/resume-rag-qa.cjs <complete-backup.sqlite>` to verify specialty → independent study question → university follow-up → unanswerable passport question against a caller-selected backup in a guarded, isolated workspace. The original workspace is never restored into or edited. A successful run requires the degree answer, Education evidence, a resolved follow-up, and abstention; answer output is retained only under ignored `work/`. Expand this set before tuning weights, adding a reranker, or changing models. GraphRAG is not implemented. The separate [day-planning agent](AGENT.md) reuses this retrieval pipeline through a read-only `search_notes` tool.
